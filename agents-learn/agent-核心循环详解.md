# Agent 核心循环深度拆解：Observe → Think → Act → Observe

## 一、这个循环的本质是什么？

Agent 循环的本质是一个**"带反馈的决策闭环"**。LLM 本身是**无状态**的——调一次，回一次，然后"失忆"。Agent 循环就是在这个无状态的大脑外面，包了一层**状态管理和执行循环**，让它能持续地跟世界交互，直到任务完成。

用前端来类比：

| Agent 循环 | 前端类比 |
|---|---|
| Observe | 读取 DOM 状态 / API 响应 / 用户事件 |
| Think | 事件处理函数里的逻辑判断 |
| Act | `setState()` / `fetch()` / DOM 操作 |
| 循环 | React 重新渲染，触发新的事件监听 |

**关键区别**：前端的事件循环是**被动**的（用户点了才触发），Agent 循环是**自主**的（自己决定下一步做什么）。

---

## 二、逐步拆解

### 第一步：Observe（感知/观察）

**在做什么？** 收集当前环境的"状态快照"，喂给 LLM 作为输入。

**具体包含什么？**
- **用户指令**：最初的任务目标（比如"帮我查一下北京明天的天气并写一封邮件"）
- **上一轮 Act 的返回结果**：比如搜索引擎返回的天气数据、API 返回的状态码
- **历史上下文**：之前几轮的 Think 和 Act 记录（存在记忆中）
- **环境状态变化**：文件被修改了、数据库更新了等

**关键细节——Observe 不是"被动接收"，而是"主动构建输入"：**

Agent 框架会把上述信息**拼装成一条结构化的 prompt** 送给 LLM。这个拼装过程本身就很重要。比如一个典型的 Observe 输出可能长这样：

```
[System] 你是一个助手，可以调用天气API和邮件API。
[User] 帮我查北京明天天气，然后给张三发邮件说这件事。
[Assistant] 我需要先调用天气API。调用：get_weather(city="北京", date="明天")
[Tool Result] {"temp": "25°C", "condition": "晴", "wind": "微风"}
```

最后那行 `[Tool Result]` 就是本轮 Observe 的核心——它把**外部世界的真实反馈**注入了 LLM 的上下文。

**Observe 最容易出问题的地方：**
- **上下文溢出**：历史太长，超出窗口限制，必须截断或总结
- **噪声干扰**：返回的原始数据太大（比如搜索引擎返回了整个网页），LLM 被无关信息淹没

---

### 第二步：Think（思考/推理）

**在做什么？** LLM 拿到 Observe 的信息后，进行推理，产出两样东西：
1. **下一步的推理文字**（"我现在知道北京明天25°C晴天，接下来应该发邮件了"）
2. **决策**：是调用工具，还是直接回复用户（结束循环）

**Think 的核心是"推理模式"，不同模式差别很大：**

| 推理模式 | 怎么想 | 适用场景 | 例子 |
|---|---|---|---|
| **ReAct** | 交替输出 Thought + Action | 通用任务 | "Thought: 天气数据已拿到，接下来该发邮件了。Action: send_email(...)" |
| **Plan-and-Execute** | 先制定完整计划，再逐步执行 | 复杂多步骤 | "Plan: 1.查天气 2.写邮件 3.发送。现在执行第1步..." |
| **Reflection** | 执行后自我评估，发现错误再修正 | 需要高质量输出 | "我生成的邮件语气太生硬了，需要重写得更友好" |

**Think 最关键的一步是"决定要不要继续"：**

LLM 每次 Think 后都会产出一个判断：
- 任务还没完 → 输出工具调用（进入 Act）
- 任务完成了 → 输出最终回复（**循环终止**）

这就是循环的"刹车机制"。如果没有它，Agent 会无限循环下去。

**Think 最容易出问题的地方：**
- **推理错误**：LLM 理解错了工具返回的数据，做出错误决策
- **陷入死循环**：反复调用同一个工具，每次都说"还没完成"
- **过早终止**：觉得做完了，但其实漏了步骤

---

### 第三步：Act（行动/执行）

**在做什么？** 把 Think 的决策变成真实的操作——调用工具、执行代码、写入文件等。

**Act 的关键：Agent 框架（而非 LLM）负责执行**

LLM 只输出"我想调用 `get_weather(city='北京')`"这个**意图**。真正去发 HTTP 请求、处理超时、解析返回值的是 Agent 框架的代码。这个分工很重要：

```
LLM 的输出（意图）：
  {"tool": "get_weather", "args": {"city": "北京", "date": "明天"}}

框架的工作（执行）：
  1. 验证参数合法性
  2. 发起 HTTP 请求
  3. 处理超时 / 错误
  4. 解析返回值
  5. 把结果塞回上下文 → 进入下一轮 Observe
```

**Act 的类型：**

| 类型 | 说明 | 风险等级 |
|---|---|---|
| **只读操作** | 搜索、查数据库、读文件 | 低 |
| **写入操作** | 发邮件、写文件、调 API 创建资源 | 高 |
| **代码执行** | 运行 Python/Shell | 很高 |

**Act 最容易出问题的地方：**
- **工具调用失败**：API 超时、参数格式错误、权限不足
- **副作用不可逆**：邮件已经发出去了才发现内容错了
- **LLM 幻觉工具**：LLM 调用了一个根本不存在的工具

---

### 第四步：Observe（再次感知）——循环的关键

这一步和第一步是同一个 Observe，但含义不同：

- **第一次 Observe**：接收用户的初始指令
- **后续 Observe**：接收 Act 的执行结果

**这个"结果反馈"就是整个循环的灵魂。** 没有它，Agent 就是一个"闭着眼睛做决策"的系统——LLM 发了个工具调用，但不知道成功了没有，只能瞎猜下一步。有了它，Agent 就变成了一个**闭环反馈系统**：

```
        ┌─────────────────────────────────┐
        │                                 │
        ▼                                 │
  [Observe] ──→ [Think] ──→ [Act] ──→ 结果反馈
  拿到天气数据   该发邮件了   调用邮件API   邮件发送成功？
        │                                 │
        └── 如果成功 → Think: "任务完成，输出最终回复"
        └── 如果失败 → Think: "出错了，换个方式重试"
```

## 三、完整示例串讲

任务："帮我搜一下 LangChain 最新版本，然后总结一下新特性"

**第 1 轮：**
- **Observe**：用户指令 "搜索 LangChain 最新版本并总结新特性"
- **Think**："我需要先搜索最新版本信息。调用 `search('LangChain latest version 2025')`"
- **Act**：框架执行搜索，返回搜索结果
- **Observe**：搜索结果包含 "LangChain 0.3.x 新增了 LangGraph Platform..."

**第 2 轮：**
- **Think**："搜索结果拿到了，但信息不够详细，我再查一下官方 changelog。调用 `fetch_url('https://...')`"
- **Act**：框架抓取网页内容
- **Observe**：网页内容返回，包含详细更新日志

**第 3 轮：**
- **Think**："信息够了，现在可以总结新特性了。不需要再调用工具，直接生成回复。"
- **Act**：输出最终文本给用户
- **循环终止**

注意：第 3 轮的 Think 做出了"**不再调用工具，直接回复**"的决策——这就是刹车。

## 四、从开发者视角看这个循环

如果要用代码实现一个最小 Agent 循环，伪代码如下：

```python
messages = [{"role": "user", "content": user_input}]

while True:
    # Observe + Think：把当前上下文送给 LLM
    response = llm.chat(messages, tools=available_tools)
    
    # 检查：LLM 决定结束了吗？
    if response.is_final_answer:
        print(response.content)
        break  # 循环终止
    
    # Act：LLM 决定调用工具
    for tool_call in response.tool_calls:
        result = execute_tool(tool_call)                        # 框架执行工具
        messages.append({"role": "tool", "content": result})    # 结果塞回上下文
    
    # 下一轮 Observe 自动发生（因为 messages 变长了）
```

整个循环就是**一个 `while True`**，退出条件是 LLM 认为任务完成。

## 五、循环中容易忽略的三个问题

### 1. 循环次数需要上限

没有上限的话，LLM 可能陷入死循环（反复调同一个工具）。实际项目中通常设 `max_iterations=10` 之类的兜底。

### 2. 每一轮的上下文在膨胀

每次 Observe → Think → Act 的结果都会追加到 messages 里。5 轮下来，prompt 可能已经几千 token 了。这就是为什么需要**记忆压缩**或**对话总结**。

### 3. "Think" 的质量决定了 Agent 的上限

工具再强，如果 LLM 推理错了（该搜索时没搜索、该停止时没停止），Agent 就废了。这也是为什么 **prompt engineering** 在 Agent 开发中依然至关重要——你本质上是在通过 system prompt 教 LLM 如何更好地 Think。

## 六、一图总结

```
用户指令
   │
   ▼
┌──────────────────────────────────────────┐
│              Agent 循环                    │
│                                           │
│  [Observe]                                │
│   接收用户指令 / 工具返回结果              │
│   拼装成 prompt                           │
│       │                                   │
│       ▼                                   │
│  [Think]                                  │
│   LLM 推理 + 决策                         │
│       │                                   │
│       ├── 需要调用工具 ──→ [Act]          │
│       │                     执行工具       │
│       │                     结果回传       │
│       │                       │           │
│       │                       └──→ 回到 Observe
│       │                                   │
│       └── 任务完成 ──→ 输出最终回复       │
│                        循环终止            │
└──────────────────────────────────────────┘
```

> **核心心法**：Agent 循环 = `while True` + LLM 决策退出条件 + 工具执行结果回传。整个架构的灵魂是 Observe 这一步——它把外部世界的真实反馈注入 LLM，让"无状态的脑子"变成了一个能跟现实交互的闭环系统。
